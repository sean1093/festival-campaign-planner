# 報告怎麼讀、怎麼交棒

`scripts/analyze_sales.py` 的輸出照這份文件解讀。腳本只負責算術，判讀責任在人。

## 參數怎麼選

### `--baseline-days N`

lift 的非促銷基準日集合。不給參數時，基準是**資料期間內所有非促銷日**——包含節後出清與長尾的低銷期，
基準會被壓低，lift 因此偏寬鬆。

給了 `N`，基準改成「第一個促銷日之前最近 N 個非促銷日」，也就是促銷啟動前的正常期。

- 選法：挑一段**需求結構與促銷期相近**的期間，且長度覆蓋完整週循環（7 的倍數最安全，例如 14、28），
  避免只取到平日或只取到週末。
- 資料本身沒有足夠的促銷前非促銷日時，腳本會在該節印出警示並自動退回可用範圍，不會靜默改定義。
- 兩種基準都跑一次，把差距寫進報告，比只報一個數字誠實。

### `--top N`

商品排行與單日排行的名次數，預設 5。品項多的時候調大（例如 `--top 20`）才看得出長尾集中度。

## 逐節讀法

| 小節 | 讀出什麼 | 這一節不能讀出什麼 |
| --- | --- | --- |
| 資料品質 | 略過幾列、原因分布、欄位對應結果、有沒有無紀錄的日期 | 資料正確與否；欄位定義是否含稅、是否已扣退貨 |
| 總覽 | 期間、天數、總額、平均日銷、加權均價 | 客單價 AOV（需要訂單筆數，這份資料沒有） |
| Promotional lift | 促銷日與非促銷日的平均日銷差異，以及各通路是否一致 | 促銷的增額效果；因果 |
| 銷售高峰 | 最熱的 7 日窗口與單日名次落在檔期的哪個位置 | 為什麼熱（可能是促銷、發薪日、連假或補貨） |
| 通路貢獻 | 各通路的金額佔比與促銷／非促銷平均日銷落差 | 通路值不值得投；成本不在資料裡 |
| 促銷類型比較 | 哪一種機制在當時賣得多、樣本夠不夠 | 哪一種機制比較有效（沒有同期同通路對照） |
| 商品排行 | 銷售集中在哪幾個 SKU、前 N 名佔多少 | 毛利貢獻；排行看的是營收不是利潤 |
| 節後衰退 | 高峰後幾天跌破 50%／20%，長尾多長 | 衰退原因（需求結束、缺貨、下架、停投都長一樣） |

判讀時優先看警示：標了「樣本不足，僅供參考」的列，天數少到一次缺貨或一場雨就能翻轉結論，
不要拿它下決策；有「無紀錄日期」警示時，滾動窗口與節後衰退把那些天算成 0，結論會被拉低。

## 三句結論（交棒 festival-campaign-plan 用）

計畫書只需要三句話。每句都要附**數字 + 資料期間 + 出處小節**，缺一項就退回重寫。

1. **節奏**：高峰落在哪幾天、佔整期多少、節後幾天跌破一半。
   → 決定預熱起點、主推日與收尾出清的時間點。
2. **資源**：哪個通路貢獻最大、哪個通路對促銷反應最好、各通路 lift 是否一致。
   → 決定預算與人力分配；各通路 lift 差距大時，全站數字不能單獨拿去報告。
3. **機制**：哪種促銷類型當時賣得最多、樣本幾天、相對非促銷基準幾倍。
   → 決定主機制；樣本不足要在同一句話裡寫出來。

三句之後接一句限制聲明，把報告最後「這份分析不能證明什麼」的重點帶進計畫書。
需要 ROI、毛利、市場規模時：這些數字不在銷售明細裡，一律標「待填」，
由使用者的成本資料或標明出處的外部報告填入，不准用假成本回推。

## lift 的三個陷阱

### 1. 基準期選得不對

拿淡季、節後出清期或含大量無紀錄日的期間當基準，lift 一定漂亮，但那是基準太低，不是促銷有效。
基準要挑需求結構相近、長度覆蓋完整週循環的期間，並在報告裡寫明基準怎麼定義。

### 2. 季節性

節慶檔期的需求本來就會上升，這段自然漲幅不是促銷的功勞。同期還有平台大促、對手動作、
天氣、發薪日與連假位置一起作用，這份資料無法把它們分離。
可做的補強：跟去年同檔期的同一段相對位置比（用 `${CLAUDE_PLUGIN_ROOT}/shared/backplan.py` 對齊 D-x，
不要用日曆日對齊，也不要自己推算節慶日期），並明說這只是縮小干擾，不是排除。

### 3. 通路混淆

各通路的客群、定價與補貼條件都不同。促銷期若通路組合改變（多開一個高單價通路、
或平台給了流量），全站數字會動，但那不是機制的效果。
所以 lift 表一定分通路各算一次：各通路方向一致才敢說機制有效；某一通路特別高，
先查那個通路當期是不是有平台補貼或資源位。

另外，同一天同時有促銷與非促銷紀錄時，腳本把整天算作促銷日，會讓 lift 偏低。
報告會提示這種混合日的天數；要精確比較就把資料拆到通路或 SKU 層級再跑。
